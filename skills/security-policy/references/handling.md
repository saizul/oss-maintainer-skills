# Handling a vulnerability report

## 1. Acknowledge (within the time in SECURITY.md)

> Thanks for the report. We've received it and are looking into it. We'll reply with
> an assessment within N working days. Please keep the details private until a fix is
> released; we'll credit you in the advisory unless you prefer otherwise.

## 2. Assess privately

- Reproduce on the supported versions. Work in a local branch that you do not push to
  the public repository.
- Decide: valid vulnerability, valid but low impact (hardening), or not a vulnerability
  (explain why, kindly).
- Estimate severity with CVSS (GitHub's advisory form has a calculator).

## 3. Fix in private

- Open a **draft security advisory**: Security tab > Advisories > New draft advisory
  (reports received through private vulnerability reporting already arrive as one).
- From the draft advisory, create a **temporary private fork**, push the fix there and
  invite the reporter if they want to review.
- Add a regression test. Keep commit messages neutral ("fix: validate path input").

## 4. Request a CVE and release

- In the draft advisory, fill affected and patched versions, then request a CVE
  (GitHub is a CVE Numbering Authority for advisories in public repositories).
- Merge the private fork, release patched versions for every supported line, and
  publish packages.

## 5. Publish

- Publish the advisory. Dependabot alerts then reach downstream users.
- Add a "Security" entry to the changelog linking the advisory and crediting the reporter.
- If needed, post an announcement with upgrade instructions.

## What counts as a vulnerability (examples for SECURITY.md)

Write project-specific bullets. Examples:

- Remote code execution, injection (SQL, command, template) or path traversal
- Authentication or authorization bypass; access to another user's data
- Secrets, tokens or personal data leaking into logs, errors or responses
- Signature or integrity checks that can be bypassed
- Denial of service with a small crafted input (decompression bombs, regex backtracking)

Usually not vulnerabilities: issues requiring an already-compromised machine,
missing hardening headers on a demo site, vulnerable dependencies with no reachable
code path (still worth updating), and reports generated by scanners without a
proof of concept.

## Supported versions: picking a policy

| Project stage | Suggested policy |
| --- | --- |
| 0.x, single maintainer | latest release only |
| 1.x, small team | latest minor of the latest major |
| widely used | latest minor of the current and previous major, for 12 months |

Promise only what you can deliver; a smaller honest policy beats an ambitious one.
